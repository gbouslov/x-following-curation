<daily_reading>
Choose a question before opening X. Examples: “Which repetitive service work is getting rebuilt?”, “What prevents an enterprise pilot from being deployed?”, “What would I need to know before buying this business?”

| Minutes | Action |
|---|---|
| 0–2 | Pick one question and the one or two Lists most likely to answer it |
| 2–9 | Read those Lists; open original threads and substantive linked sources |
| 9–12 | Bookmark at most three posts with a concrete example, useful disagreement or operating detail |
| 12–15 | Write one implication and one thing to check; close X |

An example beats a slogan. Prefer “this is where the workflow broke, and this change helped” over an unsupported revenue screenshot. Keep technical depth in the original source; write the saved note in the language of the decision.
</daily_reading>

<curation>
**Weekly, ten minutes:** inspect ten accounts, using up to ten recent authored posts per account. Replies can be useful when context is clear. Exclude reposts from judging the person's own expertise. Quiet specialists do not need daily posting to earn a place.

| Tier | Decision rule | Action |
|---|---|---|
| Keep | Recent relevant examples, informed disagreement or specialist judgment the user actually uses | Keep; put the person on the right List |
| Review | Mixed topics, limited accessible samples, a new direction, or a relationship the user values | Keep for now; try List-only or mute reposts; revisit after two weeks |
| Unfollow | Repeated irrelevant/promotional material, manipulative engagement, or duplicated coverage with no added value | Show concrete examples and ask the user before removing |

Use four questions: does it fit the user's question; is it first-hand or linked to the original work; does it add something distinct; is its volume worth the attention? Do not turn these into a fake numerical score. Follower count and verified badges are not substitutes for reading.

For a proposed change, return `handle | keep/review/unfollow | specific reason | sample URL/date | proposed action`. Also preserve a user-chosen **do not remove** list locally for friends, colleagues or other important relationships. Never infer those relationships yourself or share them with another user.

Judge the feed, too: inspect the last ten saved items. If none improves a business question or decision, replace noisy sources rather than extending the reading session. If all ten agree, add one credible counterview and check the original material behind the disagreement. Freshness is topic-specific: model capability claims age faster than a business-buying principle.
</curation>

<expansion>
The eight topical Lists are menus for questions, not a mandate to follow everyone. Start small. Expand a topic when the user can name what is missing. Read a prospective account's latest posts plus a substantive example before adding it. A failed search is not proof of inactivity. After 60 days, recheck packaged examples before describing a person as currently active.

For full-day overload, skip live browsing: have the user supply a few saved original links/texts and follow `saved-posts.md`. This preserves the learning habit without depending on the recommendation feed.
</expansion>

## Lessons from real reviews

- Recent-post samples often exist for only part of the graph. A classification without them is a bio-and-name guess, so mark those accounts review rather than unfollow.
- Famous accounts and accounts outside the main topic get over-flagged. Check whether they answer one of the user's questions before proposing removal.
- Sellers and promoters in the user's own market can be useful market research. Ask before cutting them.
- Candidate lists from different searches overlap. Deduplicate by account ID before counting.
